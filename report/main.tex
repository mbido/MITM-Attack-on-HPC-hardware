\section{Parallelization of the Direct MITM Attack}
To parallelize the given sequential algorithm, we used a sharding technique
that divides the dictionary into equal parts among the MPI processes. Each
process will have a pair \( x \rightarrow f(x) \) (or \( z \rightarrow g(z) \))
in its shard if \( f(x) \) (or \( g(z) \)) is equal to the process rank modulo
the number of processes. This way, we can ensure that each process will have a
set of pairs \( x \rightarrow f(x) \) with no elements in common with other
processes. Additionally, since we assume that \( f \) and \( g \) are uniformly
distributed, we can also assume that the shards will be approximately equal in
size. \\

For the implementation of the parallelized algorithm, we used two different methods. The first
one uses MPI to comunicate buffers computed by each process using OpenMp threads. The second one uses OpenMP
threads only with no communications. In both cases, to execute the attack, we will ask mpirun to
run the program with one process per physical CPU (one process per socket). This way, each
process will havec its memory allocated and the CPU will use its cores to run the OpenMP threads which
are faster for shard memory access.

\subsection{MPI + OpenMP Implementation}
The idea behind this implementation is to divide the domain in equal parts amoung the MPI processes.
Each process will compute different f(x) (and g(z)). Each process will use threads to compute its part,
if the element computed is contained in the process' shard, it will be directly stored in the shard and
if it is not, if will be stored in a buffer corresponding to the right process rank. Once all the elements
are computed, the buffers are sent to the right process using MPI communications.

\subsection{OpenMP Implementation}
The idea behind this implementation is that the comunications are very slow and maybe we can avoid them
completely. The idea is that each process will compute the whole domain and only store the elements that
are in its shard. This way, we can avoid the MPI communications but also,
in this way, we use way less data than the MPI + OpenMP implementation because we only store the shards
and no buffers.

\section{Performance Analysis}
For the performance analysis we ran the two algorithms on the Nantes and Rennes clusters of grid5000.

For Nantes, we used 100 nodes with each 1 socket and 18 cores per socket (that is 1800 cores in total)
and 96GiB of RAM per nodes (that is 0.9TB in total) 6 hours at night.

For Rennes, we used 29 nodes with each 2 sockets and 26 cores per socket (that is 1508 cores in total)
and 384GiB of RAM per nodes (that is 10.9TB in total) for 6 hours at night.

\subsection{Workload scaling}
The workload scaling is the mesurement of the evolution of the execution time of the
program with the number of processes being fixed and the input incressing in size.
We will, in this section we compare the
execution time evolution of our two implementations.

In those figures, \textit{Figure \ref{fig:rennes_workload}} for the mesurement on the cluster at
rennes and \textit{Figure \ref{fig:nancy_workload}} for the mesurement on the cluster at
nancy, we can see that the implementation using MPI + OpenMP is far slower than
the implementation using OpenMP only. This is due to the fact that computing f(x)
and g(x) is quite fast and the MPI communications are very slow with a
lot of nodes communicating. \\

Also we did not manage to run the MPI + OpenMP implementation with n > 38 on the clusters
because it was using to much memory for what was available. Similarly, we did not manage to run
the OpenMP implementation with n > 39. \\

However, \textit{Figure \ref{fig:nancy_strong}} and \textit{Figure \ref{fig:rennes_strong}}

is very slow with a small number of processes because of the communications with
big buffers especially with two processes. \\

We can also see that with more processes, the MPI + OpenMP implementation is less
and less far from the OpenMP only implementation speed. We can assume that this
is because the OpenMP only implementation has to compute the whole domain and
is bounded by those computations and so with a big number of processes, it cannot
go faster as every processes do the same computation on the whole domain. \\

\section{Conclusion}

With the analysis of our mesurements on the performance of our two implementations,
we can see that the OpenMP only implementation being the easiest to implement
is also the best to answer our problem. And even if it needs to compute the whole
domain, can still be scaled to bigger numbers because it computed for around 18
minutes only for n = 39 at Rennes cluster.

However, our MPI + OpenMP implementation is far from being the best solution using
MPI communications. We can imagine using smaller buffers and do the communications
during the computation loop of the parts of the domain. It would be more efficient
but if we want to use OpenMP threads to compute the domain, it becomes very
difficult to mix MPI communications and computations in a multithreaded loop.
